SECTION ONE

The terminal

Same computer, same files. The difference is that you type instead of click, and typing can be written down and repeated.

What it is

A second window onto the folders you already have.

holden@laptop climate-data-foundations % ls
README.md    data/        notebooks/
environment.yml           reference/

The idea

That listing is your course folder. Open the same folder in Finder or File Explorer and you see the same names as icons. Two views, one set of files.

Why bother

Because a click can't be written down. "Double-click the third folder, then sort by date" is not something anyone can repeat. ls data/raw/pier is.

Anything in this course you need to do twice ends up as text for that reason.

Opening it

Where to find it on your machine.

macOS

Press ⌘ + Space, type Terminal, press Return.

It also lives in Applications → Utilities, but nobody navigates there twice.

Windows

Press Start, type PowerShell, press Enter.

Use PowerShell, not the older black cmd window. PowerShell understands the same commands we'll use on the Macs.

Everyone — do this now

Open the terminal on your own laptop using the box that matches your machine. You should get a window with a line of text and a blinking cursor.

The words before the cursor will be different on every laptop in this room. That is fine; it's just a label saying who you are and where you are.

The one in VS Code is the same terminal

Later you'll notice VS Code has a panel at the bottom that looks like this. It isn't a different program or a lesser version. It's the same terminal, opened inside your editor.

View → Terminal, or Ctrl + ` (the backtick key, top-left of the keyboard).

Use whichever you like. The VS Code one is already standing in your project folder, which saves you a step.

The part to hold onto

You are always standing somewhere.

Four commands

pwd — where am I?
ls — what is here?
cd folder — go in.
cd .. — go back up.

Two shorthands

~ means your home folder. . means right here.

Everyone — type these, one at a time

pwd
ls
cd Desktop
pwd
cd ..

Press Return after each. Watch what pwd says before and after the cd. You just walked into a folder and back out without clicking anything.

Why this comes back later

Python has a current folder too, and forgetting that causes more errors this week than anything else. pwd in the terminal and Path.cwd() in Python ask the same question.

The two tricks that save the most time

Never type a path by hand.

Tab completion

Type the first few letters of a name and press Tab. The terminal finishes it for you.

cd note⇥      →  cd notebooks/

If nothing happens, what you typed matches nothing, which is itself useful. Press Tab twice to see the options.

Drag the folder in

Type cd and a space, then drag a folder from Finder or Explorer onto the terminal window. Its full path appears, spelled correctly.

Fastest way out of "I don't know where my course folder is."

Up-arrow

Press ↑ to bring back the last command. Nobody retypes anything.

Getting unstuck · staying safe

Two escapes and one rule.

It's frozen / it won't stop

Ctrl + C cancels whatever is running and gives you the prompt back. Ctrl, not Command, even on a Mac.

The screen is a mess

Type clear. Nothing is lost; the text scrolls away.

It's asking me something and I can't type

Some prompts hide what you type, which is normal for passwords. Others open a text editor you did not ask for. If you land somewhere that won't let you leave, it's usually vim: press Esc, then type :q! and Return.

The rule

Don't paste a command you can't read, especially one containing sudo, rm -rf, or curl ... | bash. Any of those can delete files or install software with no confirmation and no undo.

That goes for a forum post, a blog, or an AI. Ask what the line does first. The answer takes two seconds and costs you nothing.

What it means

What actually happened

A missing colon, an unclosed bracket or quote, or a body that is not indented. The reported line is often one line after the mistake. Python only notices when it reaches something that can't follow.

First thing to check

Look at the line above the one it names. Count your brackets and quotes there.

Not an error

A warning is not a failure.

UserWarning: h5py is running against HDF5 2.2.0 when it
was built against 2.1.0. This may cause problems.
RuntimeWarning: Mean of empty slice

How to tell them apart

An error stops the cell; nothing after it ran. A warning doesn't stop anything. Your code kept going and produced a result.

So do you ignore it?

The first one, yes. It's noise from our install and you'll see it all week. The second, no. "Mean of empty slice" means you averaged nothing at all and got nan back, which will poison every number downstream.

The habit

Read every warning once. Decide whether it's about your setup or about your data. Only the second kind matters.

The first sixty seconds

Diagnose before you change anything.

1 · Read the last line in full

Name the error type and the quoted value. You have now named the symptom. Don't touch the code yet.

2 · Print one thing

Every error in this section was answered by a single print: a path, a column list, a type, a length.

print(Path.cwd())
print(list(pier.columns))
print(pier.dtypes)
print(len(x), len(y))

3 · Then change one thing

One edit, re-run, read again. Changing three things at once means you won't know which one worked.

If you hand it to an AI

Paste the whole traceback, the line you ran, and what you expected. "My code doesn't work" gets you a guess. And you now know enough to check whether the reply addressed the last line or just rewrote your code until the red went away.

What that one line bought you

The idea the whole notebook rests on

A URL is a request, not an address.

You are filling in a form

There's a web page with checkboxes and date pickers that builds this string for you when you click Submit. Every part above is one of those boxes.

So why type it?

Because the string is the record. You can paste it into your notes, change one date and re-run it next year, or send it to a collaborator who will get byte-for-byte what you got. A sequence of clicks does none of that.

Run it now — notebook section 2

The discipline

Acquire once. Then never touch it again.

# The two-line guard you'll see in the notebook
if destination.exists():
    print("Already have it; not re-downloading.")
else:
    urlretrieve(request_url, destination)

Why not just download every time?

You are a guest on someone's server. CDIP is a public service run on a budget. A cell you re-run forty times while debugging a plot is forty requests, and that is how an IP address gets blocked.

It's also slower. The real reason is that the server's answer can change: a nowcast updates. Re-download halfway through an analysis and your figure and your numbers no longer come from the same data.

Run it now — notebook section 3

Run the download cell. About one second, about 43 KB.

Then run the very same cell a second time and read what it prints. It doesn't download again. That is the guard on the left doing its job.

Raw stays as received

What the provider sent goes in data/raw/ and is never edited, not to fix a header and not to delete a bad row. Every cleaned-up version you make goes in data/processed/.

The failure that doesn't announce itself

A download can succeed and still be wrong.

% ls -l data/raw/mop/
-rw-r--r--  1 you  staff   412  D0513_2026-07-01.nc

# 412 bytes. A week of wave data is not 412 bytes.

% head -c 200 data/raw/mop/D0513_2026-07-01.nc
<html><head><title>400 Bad Request</title>
<body>Invalid time range requested…

What happened

The server rejected the request and explained why, in HTML. Python saved the explanation into a file named .nc and reported nothing wrong, because from its side nothing was: it asked for bytes and it received bytes.

SECTION FOUR

Git & GitHub

Two reasons to care: it's how you get other people's work, and how you stop being afraid to change your own.

The distinction everyone trips on

Git is the tool. GitHub is the website.

git · on your computer

A program that watches one folder and remembers every version of it you have chosen to save. It works with no internet and no account.

GitHub · in the world

A website that hosts those folders so other people can read them, copy them, and suggest changes. Other sites do the same job: GitLab, Bitbucket, Codeberg.

Why the confusion is worth clearing up

You can use git on your own laptop and never push anything anywhere. You can also take things off GitHub without committing anything yourself, which is what you'll do in a few minutes.

A repository — "repo"

A folder that git is watching. Our course is one. Every project you find online is one.

The vocabulary, before we use any of it

Nine words, so GitHub stops looking like a foreign language.

WordWhat it actually means

You need clone in about five minutes. The rest are for reading pages without feeling lost.

The reason that matters for your master's

This is how you get other people's work.

You'll meet this constantly

A paper ends with "code available at github.com/…". A method you need has a published implementation. Your advisor says "there's a toolbox for that."

All three are repos. Cloning gets them onto your machine with their history, documentation and examples intact.

What to look at before you trust one

When was the last commit? Something untouched for six years may not run. Is there a README? Is there a license? No license means you have no formal permission to reuse it, which matters before it goes in a thesis.

The second reason

Once your own work is in git, you stop being afraid of it. You can delete a section, restructure an analysis, or try something reckless at 11pm, because every earlier version is still there and reachable.

Nobody writes analysis_final_v3_ACTUALLY_FINAL.py twice after learning this.

Setting up your own machine

Two things, once, and then never again.

1 · Tell git who you are

% git config --global user.name "Your Name"
% git config --global user.email "you@ucsd.edu"

2 · Let your machine prove it's you

% gh auth login

What the first one does

Stamps your name and address onto every commit you make on this machine. Set it before your first commit or you'll be rewriting history later.

Why the second one is needed

Cloning a public repo needs nothing. Pushing needs proof you are allowed to. GitHub stopped accepting account passwords for this in 2021, so if a prompt asks for your GitHub password and then rejects it, that is why.

Two ways through it: the GitHub CLI above, or install GitHub Desktop and sign in there, which sets the same thing up with no terminal at all.

Each project gets its own history, so "which version of the code made this figure" has an answer that is not tangled with three other projects. You can share one without handing over everything else. And when a project ends, it stops changing.

Starting one

Make the folder, then git init inside it. Or make the repo on github.com first and git clone it down, which is easier because the connection is already set up.

Write the README on day one, even if it's three lines. It's the only part future-you is guaranteed to read.

The one thing to set up early

A .gitignore listing data/raw/ and anything large. It's much easier to keep a big file out than to remove it after it's in the history.

Today we are ignoring all of this

In a minute we put a folder straight on your Desktop, where everyone can see it appear. That is for the demo, not because it's tidy.

Sort your folders out this weekend, when nobody is watching and nothing is on a timer.

For your own projects

Saving your own work is three commands.

What a commit is

A save point with a note attached. status asks what changed, add chooses what to include, commit writes it down, push sends it to GitHub.

The message is what you are actually saving

"Updated stuff" tells future-you nothing. Write down why you made the change. The diff can always show what changed; it can never tell you why.

Two things that must never go in

Big data files. Repos are for code and small text, which is why data/raw/ is ignored in ours.

Passwords and API keys. Once pushed, treat a key as public forever. Deleting it later doesn't remove it from the history.

Why anyone bothers with the website part

It's the least painful way to work with other people.

Sharing

A repo URL is the unit of exchange. It goes to your advisor, into a paper's data availability statement, or to whoever inherits the project after you.

It replaces emailing analysis_v4_final.zip and hoping nobody opens the wrong one.

Collaborating

Two people, one repo. Each works on a branch, opens a pull request, and the other one comments on specific lines before it merges.

That is exactly how the notebooks you are about to clone arrived, review comments and all.

Not losing things

Pushed work exists somewhere other than your laptop. Repos start private; you can make one public the day you publish.

Issues are for writing down a bug rather than messaging it to someone who will forget.

You don't need any of this today. You'll need all of it by spring.

Notebook 046

The Lorenz attractor.

Everyone — open notebook 046 now

  1. Open course-reference/notebooks/046_lorenz.ipynb. The new folder, not your own.
  2. Kernel: climate-data-foundations.
  3. Run the first cell. It installs a drawing package and prints a version. Up to a minute.
  4. Run the next two cells. This picture appears on your screen.

What the model is

Three equations for a layer of fluid heated from below: warm fluid rises, cools, sinks, turns over. A drastically simplified atmosphere.

No randomness anywhere in it. Same starting numbers, same result, every time.

What you are looking at

One continuous line, not a shape someone drew. It never settles down, never repeats a loop, and never leaves this region.

The question the notebook asks

If it's completely deterministic, why can nobody predict it? That is the next two slides, and it's why weather forecasts have a horizon.

046 · where it came from

Chaos was found by retyping a number.

Winter 1961, MIT

Edward Lorenz was running a twelve-variable weather model on a Royal McBee LGP-30, a desk-sized vacuum-tube machine. He wanted a longer look at one run, so instead of starting over he typed values off the printout and restarted from the middle.

The machine held six decimal places. The printout showed three. Where it had been carrying 0.506127, he entered 0.506.

The forecast came back different

Not slightly different. Within a couple of simulated months the two runs shared no weather at all. His first assumption was a failed vacuum tube.

The 1963 paper that came out of it, Deterministic Nonperiodic Flow, strips the model down to the three equations in this notebook, reduced from earlier work by Barry Saltzman.

Where the butterfly came from

Lorenz had been using a seagull. The title of his 1972 talk, Does the Flap of a Butterfly's Wings in Brazil Set Off a Tornado in Texas?, was written by Philip Merilees, who was convening the session and needed a title when Lorenz did not supply one. He wanted the alliteration.

That the plotted shape also resembles a butterfly is a coincidence, and it did the name no harm.

Why a climate course cares

This is the reason weather forecasts stop at roughly two weeks. The limit is not the model, the computers, or the density of observations. Halve every measurement error and you buy days, not months.

046 · the failure hiding in the notebook

A measurement that stops measuring.

Read the axes first

Across: time inside the model. Not days. The model has its own clock.

Up: how far apart the two runs are, measured as one number. Zero means identical.

The up axis is a log scale. Each labeled line is ten times the one below it, not one more. From 10⁻⁸ up to 10², that is ten billion-fold across the height of the plot. A normal axis couldn't show both ends at once.

What the straight part means

On a log axis, a straight line means the gap is multiplying at a steady rate rather than adding. That is what chaos means in practice: a difference too small to measure becomes a difference the size of the whole system, in about forty of those time units.

What the flat part means

Nothing. The two runs are now as far apart as the attractor is wide, and they can't get further. The number keeps updating and stops carrying information.

Fit a growth rate through the flat part and you get a precise, meaningless answer, with no error raised at any point.

The transferable version

Any quantity with a ceiling does this: a percentage, a correlation, a sensor at the top of its range. Ask what the maximum possible value is before you trust a trend.

Notebook 047

The Mandelbrot set is a map of one question.

Everyone — open notebook 047 now

Open course-reference/notebooks/047_mandelbrot.ipynb, kernel climate-data-foundations. Run the first cell, wait for the version number, then run down to the first picture. Each image is about twenty seconds of arithmetic.

The rule, in full

Pick any point c on the plane. Start at z = 0. Then do this over and over: square z, add c. That is the entire procedure.

Either z stays near the origin forever, or it eventually runs away to infinity. There's no third option.

"The plane" just means a flat map of numbers

Every point on the left panel is a pair: how far across, how far up. That pair is one number of a kind that has two parts, and there's a rule for squaring it that mixes the two. You don't need that rule to read the picture.

So what is the picture?

Every pixel is one starting point c, colored by what happened to it. Black means it never ran away. Those points are the set. Everything else escaped, and the color says how many steps that took.

Nobody designed the shape. Nobody chose the round body or the buds around it. They are what falls out of asking that one question at every point.

And what is a "fractal"?

A shape that keeps having detail no matter how far in you zoom, and that tends to look like a smaller copy of itself when you get there.

A circle is not one: zoom in far enough and its edge looks like a straight line. This shape never does that. Zoom in a thousand times and there's just as much crinkle as before.

Coastlines behave the same way, which is where the word came from and why it turned out to matter outside mathematics.

Why the edge is the interesting part

Well inside, points obviously stay. Well outside, they obviously leave. Near the boundary you can't tell without actually running the arithmetic, sometimes for thousands of steps.

That is why a picture of this takes real time to compute, and why nobody had one until computers existed.

047 · where it came from

Worked out in 1918. Not seen until 1980.

1918 Two French mathematicians, Gaston Julia and Pierre Fatou, work out on paper what happens when you repeat that squaring step over and over. Julia's write-up runs to nearly 200 pages of algebra. Neither of them ever saw a picture of it. Doing it by hand would have meant years of arithmetic per image. 1967 Benoit Mandelbrot asks in Science: how long is the coast of Britain? The answer turns out to depend on how long your ruler is, and it never settles on a number. He later calls shapes like this fractals, from the Latin for broken. 1978 Robert Brooks and Peter Matelski print the first picture of the set, while working on something unrelated. It's a few hundred asterisks on a line printer. You can just about tell what it is. 1980 On 1 March, at an IBM research lab, Mandelbrot gets a real computer onto it and the shape finally appears. Adrien Douady and John Hubbard prove the same year that it's all one piece: every little bud is connected to the main body by a thread, however separate it looks. They name it after him. 1990s Mitsuhiro Shishikura proves how crinkly the edge is, and the answer is the maximum possible. The boundary is a line, so you would expect it to be one-dimensional. It's so infinitely wrinkled that it behaves like a two-dimensional patch instead.

Sixty years separate the mathematics from the picture. Plotting is not decoration on top of the analysis; sometimes it's the only way to find out what your equations have been doing.

047 · the failure hiding in the notebook

Where the arithmetic runs out.

Computers keep a fixed number of digits

Like a pocket calculator that only ever shows eight digits. Ask for more and it rounds. float32 and float64 are two settings for how many digits to keep: roughly seven, or roughly sixteen.

What went wrong on the right

We asked for 460 pixels across a very narrow window, so neighboring pixels differ only in about the tenth digit. With seven digits, the computer can't tell them apart. Those 460 requests round down onto 35 actual positions, and the same answer gets copied across each block.

Notice what did not happen

No error. No warning. Nothing missing. It returned an image of the right size, in the right place, with roughly the right shape, smooth where it should have been intricate.

Sixteen digits gets you about nine more zoom levels, and then does exactly the same thing. Every setting runs out somewhere. The question is whether you notice.

045 · homework, whenever you feel like it

Getting NASA to answer you: five steps, once.

Step by step, and none of it's urgent

  1. Go to urs.earthdata.nasa.gov. Click Register, top right.
  2. Fill in the form with your UCSD email. Free, no approval wait. Write your username and password down — you need to type them in step 4.
  3. Check your email and click the confirmation link. You are not done until you have.
  4. Open a terminal. Type this all on one line, replacing the two capitalized words with yours, then press Return: 
    echo 'machine urs.earthdata.nasa.gov login MYNAME password MYPASSWORD' >> ~/.netrc
  5. Then type this and press Return. It stops anyone else on the machine reading the file: 
    chmod 600 ~/.netrc

Check that it worked

Type cat ~/.netrc. You should see your one line, with your real username and password in it. If you see nothing, step 4 did not run.

If your password has a quote or a space in it

Step 4 will misbehave. Change your Earthdata password to letters and numbers only, or ask me and we'll do it with a text editor instead.

What that file is

.netrc is a plain text file in your home folder that programs check when a server asks who you are. It has existed for forty years and many tools use it.

The point is that your password lives in exactly one place, outside the repository. Never in a notebook, never in a URL you print, never in anything you push. Notebooks get shared; this file doesn't.

Same steps, plus the dataset links and how to cite it, are written down in data/README.md under "Route 4". You won't have to remember any of this.

Why these three, and not three prettier ones

Each one hides a wrong answer that never raises an error.

045 · ccs.py → load_ccs_subset()

The file spells its missing-data marker _Fillvalue. The standard is _FillValue, capital V, so xarray ignores the attribute without saying anything.

Here you get away with it: the gaps are already blank. Had the file marked them -999, every average would have been dragged down and nothing would have warned you.

046 · lorenz.py → largest_lyapunov()

Read why that function pulls the two runs back together as it goes. Remove that and the measurement saturates, and the number it returns stops meaning anything while still looking fine.

047 · mandelbrot.py → smallest_reliable_span()

That function exists to answer "have I zoomed past what my arithmetic can do?" before rendering, rather than after squinting at a smooth image and wondering.

The pattern you should now recognize

Every error in section 2 stopped the cell and told you so. The download that returned an HTML error page did not. Neither do these three.

The failures that cost you a month are not the ones that stop the cell. They return a number of about the right size, in about the right units, pointing in about the right direction.

Go and read those three functions

Each one is about fifteen lines, and each exists because of the trap named above it. They are the most useful thing in those notebooks, and none of them is about oceanography, chaos, or fractals.

Check the magnitude, check the units, and check against something you already know. Not because you are bad at this: a plausible wrong answer looks exactly like a right one.

SECTION SIX

Durable AI context

Every new chat starts from nothing. If the only place your project is explained is inside a conversation, you'll explain it again tomorrow, and again next week.

The problem

The model forgets. Your repo doesn't.

What this looks like in practice

Session one: you spend twenty minutes explaining that SURF_TEMP_C is in Celsius, that -999 means missing, that the 1988 gap is a real instrument outage and not something to interpolate over. You get good help.

Session two, next week: none of that exists. So you re-type it, or you skip it and the model invents an answer where your explanation used to be.

The move

Write the context into files in the repo rather than into a chat. Files get read at the start of every session, they are versioned alongside the code, and your collaborators get them too.

A colleague joining your project needs the same briefing. Write it once.

You already did this on Monday

Look at data/README.md and manifest_template.yml in the course repo. We called them a folder contract and a provenance record, and their purpose was reproducibility.

They are also the briefing an AI needs in order to stop guessing about your data. The documentation and the context turn out to be the same file.

What to actually write

Three files carry most of the weight.

CLAUDE.md · AGENTS.md

At the top of the repo. Read automatically at the start of a session by most coding agents.

What the project is, in three sentences. Where data lives and where outputs go. How to run things. House rules: "never edit data/raw/", "figures go in figures/".

A map of the code

One page: what each folder is for, and which file to open for which job. This is what you would tell a new labmate in two minutes.

Generate this one rather than writing it. See the next slide.

A data dictionary

For us this is the important one. Every column: its units, its missing-value code, its real-world meaning, and the known problems.

"Depth is positive downward." "Pre-1950 values are hand-transcribed." An AI can't infer any of that, and neither can a reader.

Plain Markdown, committed alongside the code it describes.

Generating the map

Ask for it, then check it.

Why that last line matters

Without it you get confident prose about files that don't exist. A wrong map is worse than no map, because you and every future session will now believe it.

So verify it the way you verify a figure

Open the file, spot-check three claims against the repo, and delete anything you can't confirm. The output is plausible by construction, which is the reason to check it.

Then keep it alive

Every time you lose an hour to a units trap or a broken path, add a line about it to the file. You then spend that hour once instead of every year.

Where this leaves you

All six of these are the same habit.

Terminal

Say where you are, in text, so it can be repeated.

Errors

Read what the machine said before deciding what is wrong.

Data

Record what you asked for, not only what you got.

Git

Write down what changed and why, so the history survives you.

Context

Write down what you know, so you only have to learn it once.

None of it's about being clever. It's about leaving a trail you can pick up cold six months from now, when none of today is still in your head.
